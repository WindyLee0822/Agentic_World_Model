# B1 fixed-context token sensitivity

This extends the previous offline OfficeBench estimate. No B1 run or API usage logs were available. All numbers below are **counterfactual workload estimates**, using ours' 300 observed tasks and candidate actions, not measurements of B1 behavior or accuracy.

In the implementation, B1 freezes task configuration, tool documentation, selected initial state, and optional reference files before candidate actions. Each file is capped at 6,000 characters; the serialized fixed context is capped at 60,000 characters (about 15,000 tokens using chars/4), plus instructions. This is selection and truncation, not learned summarization, and does not guarantee that all task information survives. The prefix is reused by WM and verifier calls, not added to every solver call. B1's default config predicts every app action and prohibits adaptive evidence reads. B1 can still execute Python for computation and can need repair calls.

Assume a fixed data prefix F of 1k/4k/8k/15k tokens, added to the prior base local-prompt budgets. Assume one WM call per non-system action, one state call per candidate, and one whole-verdict call for candidates with recorded per-check metadata. Add recorded atomic checks separately. This removes ours' extra adaptive-call proxy; retries/repair calls are excluded. Solver histories, outputs, and comparative selection costs are held fixed. Fixed context has no additional LLM construction charge because the current implementation builds it deterministically. If an LLM is used to compress it, charge that preprocessing separately, and account for any information loss.

| N | Ours prior base | B1 F=4k | B1 F=8k | B1 F=15k |
|---:|---:|---:|---:|---:|
| 1 | 187k | 239k | 306k | 423k |
| 2 | 382k | 488k | 620k | 852k |
| 4 | 726k | 938k | 1.20M | 1.65M |
| 8 | 1.44M | 1.87M | 2.38M | 3.28M |
| 16 | 2.84M | 3.71M | 4.73M | 6.52M |

At N=1 and F=8k, B1's modeled mean/median/P90 is 306k/168k/767k; ours' prior modeled values are 187k/82k/520k. At F=1k, B1 is about 189k/task, essentially equal to the prior ours estimate. Consequently, no universal token advantage follows from the architecture; compressed prefix size and actual calls determine the result. These F scenarios vary only the B1 prefix; they are not confidence intervals or the earlier full low/high sensitivity.

Calculation from the previous managed estimate T, managed non-atomic call proxy M, direct B1 call proxy D, and atomic-check count A:

`B1 = T - (M-D)*(2500+200) + F*(D+A)`

The first adjustment removes assumed extra managed calls at the previous 2,500-input/200-output budget. The second charges the repeated fixed prefix. `same_calls_mean` in the JSON retains M instead of D as an alternative if B1 needs similar call counts. Prefix caching may reduce billed cost but does not reduce these logical input-token totals.

This is distinct from the earlier no-context-management scenario: B1 keeps a fixed prefix instead of accumulating an ever-growing raw internal transcript. There is no basis to transfer the earlier 702k N=1 ablation number to B1.

Reproduce with ` /usr/bin/python3 -S experiments/officebench_token_estimate_20260907/estimate_b1.py`. Outputs: `b1_per_task.csv` (6,000 task/prefix rows) and `b1_summary.json` (20 aggregate cells, each covering 300 tasks). A measured comparison requires actual B1 trajectories, prompt sizes, and per-call usage; this estimate makes no claim about equal success rates.
